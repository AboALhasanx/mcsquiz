## Offline and content behavior: limits visible in code

- **Offline readiness is conditional, not a cold-offline guarantee.** `loadData()` first requests the live content manifest, then reuses `portal_manifest_v1`, then fetches the bundled `data/index.json` if neither is available. Banks are loaded separately. The service worker lists the bundled index and bank files in its precache, but the browser helper used by the offline spec blocks service workers; the dedicated offline test allows them and first loads while online. See [`js/app.js`](../../js/app.js) (`loadData`, `offlineState`), [`sw.js`](../../sw.js) (`CORE`, install/fetch), and [`tests/test_offline.py`](../../tests/test_offline.py).
- **Partial precache is possible by design.** The service worker installs with `Promise.allSettled` for its `CORE` requests, so a failed asset request does not fail the whole installation. The offline spec checks that the worker takes control and that a quiz flow works after an online seed; it does not prove every precache item succeeded on every browser/device. See [`sw.js`](../../sw.js) and [`tests/test_offline.py`](../../tests/test_offline.py).
- **No bundled-bank retry after a live bank failure when there is no local bank copy.** If the chosen manifest source is the live portal, `loadData()` calls `PortalContent.bank()`. On failure it uses the versioned local-store bank only if one exists; otherwise it logs an isolated load failure and continues without that bank. It does not then fetch that chapter from the bundled `data/banks` path. The bundled index fallback does not itself guarantee a matching bundled bank is selected. This is a code-inspection limitation, not a failure reproduced in the current test run. See [`js/app.js`](../../js/app.js) (`loadData`, bank job rejection handler) and [`js/content.js`](../../js/content.js).
- **Local browser coverage deliberately does not cover the live content RPC path.** For localhost, `tests/common.py` aborts requests to `content_manifest` so the specs use bundled content rather than fan out across remote bank RPCs. That makes the local behavior tests deterministic, but they do not establish live-portal availability or live-bank fallback behavior. See [`tests/common.py`](../../tests/common.py) and [`tests/test_catalog.py`](../../tests/test_catalog.py).

## Timing cases: test evidence vs. defect claims

- **Sign-out waits for in-flight sync before local clearing.** In [`js/app.js`](../../js/app.js) the logout handler awaits `pullOrPush()` when online and then calls `signOut()` and `clearPersonal()`. [`tests/test_accounts.py`](../../tests/test_accounts.py) replaces sync with a 1.5-second promise, inspects local history/bookmarks/bests/PIN/account at 800 ms, and then asserts those local values are cleared after sync completes. This confirms the intended ordering and the intermediate state while sync is pending. The test does **not** show that data remains after logout completes, and this inspection did not reproduce a sign-out defect. It is a timing-sensitive scenario; rerun the account spec in the approved test setup if changing this flow.
- **Catalogue assertions use fixed waits.** [`tests/test_catalog.py`](../../tests/test_catalog.py) waits 300 ms after a subject switch and 800 ms after opening a quiz, then asserts active-chip/start-card state; it also checks that switching subjects emits no Supabase API requests. The test is useful evidence for those sampled transitions, but fixed sleeps are not proof of behavior under arbitrary latency. No independent catalogue timing failure was reproduced here; treat a suspected race as a hypothesis until it is reproduced with a deterministic delayed response or condition-based wait.
